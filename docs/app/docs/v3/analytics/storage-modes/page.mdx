# Storage Modes

The Analytics Store supports two storage modes for exported data: **ducklake** (default) and **parquet**. Both produce Parquet files, but differ in how they manage metadata and catalogs.

## DuckLake (Default)

DuckLake-managed Parquet files with a catalog storing metadata. This is the default storage mode.

```properties
yaci.store.analytics.storage.type=ducklake
```

### Catalog Options

Both options store the data as DuckLake Parquet files under the export path; the catalog type only
chooses where DuckLake keeps its catalog.

**DuckDB file catalog (the default, and what the `analytics` profile uses):**

```properties
yaci.store.analytics.ducklake.catalog-type=duckdb
yaci.store.analytics.ducklake.catalog-path=./data/analytics/ducklake.catalog.db
```

The exporting node is the only writer. Keep the catalog file with the export path: one is
useless without the other.

**PostgreSQL catalog**, for when other processes or hosts read the catalog while the node writes
it:

```properties
yaci.store.analytics.ducklake.catalog-type=postgresql
```

When using PostgreSQL as the catalog, it defaults to the main datasource connection. You can optionally configure a separate catalog connection:

```properties
yaci.store.analytics.ducklake.catalog-url=jdbc:postgresql://localhost:5432/yaci_store
yaci.store.analytics.ducklake.catalog-username=postgres
yaci.store.analytics.ducklake.catalog-password=pass
```

<Callout type="warning">
**Upgrading from a 3.0.0 beta.** The default was `postgresql` in the betas and is `duckdb` now. A
node that set `storage.type=ducklake` but never set `catalog-type` refuses to start when its
PostgreSQL database already holds a DuckLake catalog and no DuckDB catalog file exists, instead of
starting a new, empty catalog. Set `yaci.store.analytics.ducklake.catalog-type=postgresql` to keep
the existing catalog. If that database cannot be reached for the check, the node also refuses to
start rather than create the DuckDB catalog file; start it again once the database is up, or set
`catalog-type` either way.
</Callout>

### Characteristics

- ACID transactions, time-travel queries, schema evolution
- PostgreSQL catalog supports multi-instance deployments
- DuckDB catalog (the default) is a single local file, for a node that is the catalog's only writer
- Query tables directly by name (e.g., `SELECT * FROM analytics.block`)

### Partitioning

Every DuckLake table is created and partitioned in one transaction: daily tables by `date`, epoch tables by `epoch`. An epoch table's export query must return an `epoch` column; an export whose query has none fails with an error naming the table, and no table is created.

A table that an earlier release left without partitioning (its creation was interrupted between `CREATE TABLE` and `ALTER TABLE ... SET PARTITIONED BY`) is partitioned at its next export. If one of its data files holds more than one partition value, or a table is partitioned by a different column, the export fails with a message asking you to rebuild the table (drop it and reset its export state).

### Export verification

After each export, and before a COMPLETED partition is skipped, the writer counts the partition's rows in the latest committed catalog snapshot and compares them with the exported row count. Files on disk are not used for this check: a replaced partition keeps its old files until maintenance deletes them.

### Catalog maintenance

A replaced partition (re-export, repair) retires its old data files, but DuckLake keeps them, and all snapshots, until snapshots are expired and old files are cleaned up. A maintenance task does this once a day (`ducklake.maintenance.*`):

1. `ducklake_expire_snapshots` expires the snapshots older than `retention-hours` (default 7 days). The latest snapshot is never expired.
2. `ducklake_cleanup_old_files` deletes the files that were scheduled for deletion more than `retention-hours` ago.

A data file is therefore deleted no earlier than `retention-hours` after it stopped being part of the latest snapshot. The analytics query layer reads the latest snapshot's file list and rebuilds its views every 5 minutes, so with the default retention its views keep working unless their refresh fails for a week. Time travel to snapshots older than the retention is no longer possible.

Files that DuckLake never committed (from an export that crashed mid-write) are not deleted: the export path may also hold files DuckLake does not track, such as Parquet-mode exports.

### Catalog and export state

The export state (`analytics_export_state`) and the DuckLake catalog are stored separately. If the catalog is deleted (a missing DuckDB catalog file is recreated empty at startup), recreated, pointed at another schema, or restored from an older backup, the state still lists partitions as COMPLETED that the catalog does not have.

At startup the store compares the two (`ducklake.reconcile-state-on-startup`, default on). COMPLETED partitions with rows in the state but none in the catalog are reset to FAILED and exported again by the scheduler; this is logged at ERROR level per table. All catalog reads happen before any state is changed, so a catalog that cannot be reached changes nothing. Partitions with fewer rows in the catalog than in the state are only reported.

The same startup step also resets COMPLETED partitions that were stored with no rows although the table always has rows for a final partition: `adapot`, `epoch_param` after Byron, and `epoch` for an epoch with blocks. Earlier versions stored them too early (for example every `epoch` partition while epoch-aggr was off), and they are exported again now.

<Callout type="warning">
Re-exporting reads the rows from PostgreSQL again. If pruning has removed them there, the re-exported partitions are incomplete. Restore the catalog instead if you can.
</Callout>

## Parquet

Direct Parquet file export without a catalog. Files are organized by table name and partition (date or epoch).

```properties
yaci.store.analytics.storage.type=parquet
```

### Directory Layout

```
./data/analytics/
  block/
    date=2024-01-15/data.parquet
    date=2024-01-16/data.parquet
  epoch_stake/
    epoch=450/data.parquet
```

### Characteristics

- Simple, no external dependencies beyond DuckDB JDBC
- Files are immutable once written
- No built-in catalog metadata
- Query files using `read_parquet()` with Hive partitioning

## Choosing a Storage Mode

| | DuckLake (default) | Parquet |
|---|---|---|
| **Setup** | Requires catalog (PostgreSQL or DuckDB file) | No catalog needed |
| **Querying** | SQL table names (e.g., `analytics.block`) and `read_parquet()` with file paths | `read_parquet()` with file paths |
| **Multi-instance** | Supported (with PostgreSQL catalog) | Not supported |
| **ACID / time-travel** | Yes | No |
| **Best for** | Production, shared environments | Simple setups, ad-hoc analysis |

<Callout type="info">
For most users, **DuckLake** mode with the default DuckDB catalog is recommended; use the PostgreSQL catalog when other processes or hosts read the catalog. Use **Parquet** mode if you want a simpler setup without catalog management.
</Callout>
