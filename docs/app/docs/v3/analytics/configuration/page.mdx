# Configuration Reference

| Property | Default | Description |
|---|---|---|
| `yaci.store.analytics.enabled` | `false` | Enable analytics store |
| `yaci.store.analytics.export-path` | `./data/analytics` | Output directory for exported files |
| `yaci.store.analytics.enabled-tables` | _(empty = all)_ | Comma-separated list of tables to export |
| `yaci.store.analytics.admin.enabled` | `false` | Enable the admin REST API. It has no authentication; see [Admin API](#admin-api) |

| `yaci.store.analytics.continuous-sync.buffer-days` | `1` | UTC days the daily exports stay behind the *finalized* tip (latest block time minus the finality window). | `yaci.store.analytics.continuous-sync.finality-margin-hours` | `1` | Added to the finality window derived from genesis (`k × slotLength / activeSlotsCoeff`: 12 h on mainnet/preprod, ~2.4 h on preview) |
| `yaci.store.analytics.continuous-sync.finality-window-hours` | `0` | Override for the derived finality window (`0` = derive from genesis); the margin is still added |
| `yaci.store.analytics.continuous-sync.sync-check-interval-minutes` | `15` | Gap detection interval when fully synced |
| `yaci.store.analytics.continuous-sync.catch-up-interval-minutes` | `1` | Gap detection interval when catching up |
| `yaci.store.analytics.continuous-sync.export-after-sync` | `true` | Defer exports until the sync reaches chain tip. Set `false` to export during the sync |
| `yaci.store.analytics.continuous-sync.retry-backoff-initial-minutes` | `1` | Wait before retrying a partition whose export failed. Each further failure doubles the wait |
| `yaci.store.analytics.continuous-sync.retry-backoff-max-minutes` | `360` | Longest wait between retries of a partition that keeps failing |
| `yaci.store.analytics.pruning-check.accept-data-loss` | `false` | Keep the configured pruning windows: never raise them or hold pruning for the analytics export (see [Pruning](#pruning-and-the-analytics-store)); a warning is logged instead |
| `yaci.store.analytics.pruning-check.margin-hours` | `12` | Hours a pruning window is kept beyond the export delay (finality window + `buffer-days`) when it is raised |
| `yaci.store.analytics.parquet-export.codec` | `ZSTD` | Compression codec |
| `yaci.store.analytics.parquet-export.compression-level` | `3` | ZSTD compression level (1-22) |

| `yaci.store.analytics.ducklake.export.codec` | `ZSTD` | Compression codec for DuckLake Parquet files |
| `yaci.store.analytics.ducklake.export.compression-level` | `3` | ZSTD compression level (1-22) for DuckLake exports |
| `yaci.store.analytics.ducklake.export.row-group-size` | `-1` | Row group size for DuckLake Parquet files (-1 = DuckDB default) |
| `yaci.store.analytics.ducklake.writer-lock-timeout-seconds` | `900` | Longest wait for the single DuckLake writer connection while another export, verification or maintenance run holds it. When it expires the waiting export fails (and is retried later) instead of blocking its thread |
| `yaci.store.analytics.ducklake.reconcile-state-on-startup` | `true` | At startup, reset COMPLETED partitions that have rows in the export state but none in the DuckLake catalog, so they are exported again (see [Storage Modes](/docs/v3/analytics/storage-modes#catalog-and-export-state)) |

## Known Caveats

### Workspace-sensitive catalog path (DuckLake)

DuckLake stores `DATA_PATH` in catalog metadata. If you use a relative `export-path` (e.g., `./data/analytics`), the Parquet file paths in the catalog are relative to the working directory where yaci-store was started.

When querying with DuckDB CLI or Python, you **must start from the same working directory** as the application. Otherwise, DuckLake will fail to locate the Parquet files.

**Recommendation:** Use absolute paths in production:
```properties
yaci.store.analytics.export-path=/var/lib/yaci-store/analytics
```

### DuckDB memory usage in JVM

<Callout type="warning">
If not configured, DuckDB uses its default (80% of system RAM). It is recommended to set this explicitly in production and container environments to prevent OOM kills.
</Callout>

DuckDB defaults to using 80% of system physical RAM for its buffer manager. Since DuckDB runs inside the JVM process, this can cause memory contention — JVM heap + DuckDB buffer may together exceed available system RAM, leading to OOM kills (especially in containers/Kubernetes).

To limit DuckDB memory usage:

```properties
# Limit each DuckDB instance's buffer manager to 1GB
yaci.store.analytics.duckdb.memory-limit=1GB
```

Note: The limit applies per DuckDB instance. The export writer is one instance; the analytics query layer (if enabled) is a second one shared by all concurrent readers, so plan for up to `memory_limit * 2`. Some DuckDB aggregate functions may also allocate memory outside the buffer manager, so actual usage can slightly exceed the configured limit.

### Pruning and the analytics store

A day is exported once its oldest rows are `buffer-days × 24 h` + the finality window old: about 37 h on mainnet with the defaults. Several stores can prune PostgreSQL rows much sooner (about 12 h with their defaults), which would delete most of each day before it is exported. When the analytics store is enabled, it keeps pruning from deleting rows it has not exported yet, with no configuration needed:

| Pruning | Window property | Exported tables protected |
|---|---|---|
| `store.utxo.pruning-enabled` | `store.utxo.pruning-safe-blocks` (blocks) | `address_utxo`, `tx_input` |
| `store.transaction.pruning-enabled` | `store.transaction.pruning-safe-slots` | `transaction`, `transaction_witness`, `transaction_cbor` |
| `store.transaction.cbor-pruning-enabled` | `store.transaction.cbor-pruning-safe-slots` | `transaction_cbor` |
| `store.blocks.cbor-pruning-enabled` | `store.blocks.cbor-pruning-safe-slots` | `block_cbor` |
| `store.account.history-cleanup-enabled` or `store.account.pruning-enabled` | `store.account.balance-cleanup-slot-count` | `address_balance`, `stake_address_balance`, `stake_address_balance_snapshot` |

- **The window is raised.** At startup, a window shorter than the export delay plus `pruning-check.margin-hours` (default 12) is raised to that value: 49 h on mainnet, which is 176,400 slots, or 8,820 blocks for UTxO pruning. The change is logged at WARN with the value to configure to silence it.
- **Pruning is held while the export is behind.** While the indexer is still syncing with `continuous-sync.export-after-sync=true` (nothing is exported yet), or while a day that is ready to export has not been exported (for example a failed export waiting for its retry), these pruning features delete nothing. They resume, with their window, once the export has caught up. So an initial sync with pruning on keeps all rows until they are exported, and PostgreSQL holds the whole history until then.
- `yaci.store.analytics.pruning-check.accept-data-loss=true` leaves the configured windows alone (never raised, never held), and only warns about the rows the analytics store will miss.

Reward and epoch-stake pruning are not managed: both follow the AdaPot jobs that the same tables wait for. Custom exporters are not covered.

### DuckLake requires `public` schema in PostgreSQL

DuckLake stores its metadata tables in the `public` schema. The application automatically creates this schema if it doesn't exist. If your PostgreSQL instance restricts schema creation, ensure `public` exists before enabling DuckLake.

## Admin API

The admin API provides manual control over exports when enabled (`yaci.store.analytics.admin.enabled=true`).

<Callout type="warning">
The admin API has no authentication, and its endpoints export, re-export and reset data. Do not expose it outside a trusted network: keep the port private, or put an authenticating reverse proxy in front of `/api/v1/analytics/admin/**`. The shipped `analytics` profiles enable it.
</Callout>

| Method | Endpoint | Description |
|---|---|---|
| GET | `/api/v1/analytics/admin/tables` | List all registered exporters |
| GET | `/api/v1/analytics/admin/status` | Current sync status (see below) |
| GET | `/api/v1/analytics/admin/statistics/{table}` | Export statistics for a table |
| POST | `/api/v1/analytics/admin/export/date/{date}` | Export all daily tables for a date |
| POST | `/api/v1/analytics/admin/export/table/{table}/date/{date}` | Export specific table for a date |
| POST | `/api/v1/analytics/admin/export/table/{table}/epoch/{epoch}` | Export specific table for an epoch |
| POST | `/api/v1/analytics/admin/export/table/{table}/range` | Backfill date range |
| POST | `/api/v1/analytics/admin/export/table/{table}/epoch-range` | Backfill epoch range |
| POST | `/api/v1/analytics/admin/repair/table/{table}/range` | Re-export a date range of a daily table |
| POST | `/api/v1/analytics/admin/sync/trigger` | Trigger immediate gap sync (409 if a sync is already running) |
| DELETE | `/api/v1/analytics/admin/state/{table}/{partition}` | Reset the export state of one partition: `2024-01-15`, `date=2024-01-15`, `450` or `epoch=450` |
| DELETE | `/api/v1/analytics/admin/state/{table}/range?startDate=&endDate=` | Reset the export state of a daily table's days from `startDate` to `endDate` (inclusive, `yyyy-MM-dd`) |
| DELETE | `/api/v1/analytics/admin/state/{table}/epoch-range?startEpoch=&endEpoch=` | Reset the export state of an epoch table's epochs from `startEpoch` to `endEpoch` (inclusive) |

### Readiness

Manual exports and repairs use the same readiness check as the scheduler, so a partition is never stored as `COMPLETED` before its data is final:

- A **day** can be exported once it is on or before the export end date: the finalized tip (latest block time minus the finality window) minus `continuous-sync.buffer-days`. `GET /status` reports it as `exportEndDate`. Today, a future day, or any range or repair that ends after the export end date is refused.
- An **epoch** that has not started is refused. Beyond that, each epoch table has its own condition, for example the AdaPot job of the epoch (see [Built-in Table Exporters](/docs/v3/analytics/overview#built-in-table-exporters)). `epoch`, `mir`, `instant_reward` and custom epoch exporters without `depends-on-adapot-job` wait until the epoch has ended and its last slot is older than the finality window.
- A table that cannot be exported with the current configuration (for example an AdaPot table with adapot disabled) is refused.

Nothing is exported or marked for a refused partition.

### Resetting export state

A reset deletes export-state records only; the exported data stays until the partition is exported again, and that export replaces it. Both reset endpoints return `404` when there was no state to reset (for example a day that was never exported), and `400` for a partition or date that cannot be parsed or does not match the table's partitioning.

### Status codes

| Status | When |
|---|---|
| `200` | Exported, or already exported. Range responses list the partitions that were not ready (`notReady`) or failed (`failed`) |
| `400` | Invalid input: a date that is not `yyyy-MM-dd`, a day before genesis, a negative epoch, `start` after `end`, a range larger than `admin.max-range-days` / `admin.max-range-epochs`, or a table whose partitioning does not match the endpoint |
| `404` | Unknown table, or no export state to reset |
| `409` | The partition or the end of the range is not ready (see above), another manual export or repair is running (one runs at a time), or `POST /sync/trigger` while a sync is running |
| `500` | A single-partition export failed; the partition is `FAILED` and the scheduler retries it |

Refused requests return a JSON body such as:

```json
{"status": 409, "error": "Conflict", "message": "date=2026-11-16 is not final yet: the latest day that can be exported is 2026-11-14 (the finalized tip minus buffer-days=1)"}
```

### Sync status and retries

Only partitions that can be exported now count as missing. An epoch whose AdaPot job has not run yet (for example the current and previous epoch of `reward`), or any AdaPot-gated epoch when AdaPot is disabled, is reported in `notReadyCount` and is not a gap. `isFullySynced` is true when no exportable partition is missing, and the scheduler then checks every `sync-check-interval-minutes` instead of every `catch-up-interval-minutes`.

A partition whose export failed is retried after `retry-backoff-initial-minutes`, doubling after each further failure up to `retry-backoff-max-minutes`; while it waits it is counted in `retryPendingCount` (and still as missing). The scheduler logs at INFO only when the set of missing partitions changes or when it exports something.

Only one sync runs at a time; `POST /sync/trigger` returns 409 while the scheduled sync (or another trigger) is running. Two exports of the same table and partition never run at once: the second one fails with "already being exported".

### Example: Export and query a specific date

```bash
# Trigger export for a specific date
curl -X POST http://localhost:8080/api/v1/analytics/admin/export/date/2024-01-15

# Query the exported data
duckdb -c "SELECT COUNT(*) FROM read_parquet('./data/analytics/transaction/date=2024-01-15/*.parquet');"
```
