# Snapshot Export and Import

Bootstrap a Yaci Store PostgreSQL database from a packaged Parquet snapshot instead of syncing the
chain from genesis.

<Callout type="warning">
This feature is ready for manual preprod qualification, not a claim of production or mainnet
readiness. Automated tests cover import, resume, export, and the review fixes. The updated lossless
stake-balance path still needs a full network restore and live acceptance run. Snapshots are
unsigned and retain the [declared limitations](#known-limitations).
</Callout>

## Prerequisites and starting the CLI

Use the same build for the source exporter, target Yaci Store, and admin CLI. The initial format
requires PostgreSQL and a migrated target schema. Import supports a subset of stores, selected
from the target application’s enabled modules. Keep a separate source and disposable target configuration for qualification.

From a source checkout, build with Java 21:

```bash
./gradlew :applications:admin-cli:bootJar :applications:all:bootJar
```

Launch the CLI jar from `applications/admin-cli/build/libs` using your source configuration:

```bash
java -jar /path/to/yaci-store-admin-cli.jar --spring.config.additional-location=file:/path/to/source.properties
```

Use the matching `target.properties` file when importing, validating, or applying indexes. Each
file supplies the usual `spring.datasource.url`, username, password, and network settings. The
schema is selected by `currentSchema` in the PostgreSQL JDBC URL, for example
`jdbc:postgresql://localhost:5432/yaci?currentSchema=snapshot_test`. For preprod, set
`store.cardano.protocol-magic=1` in both configurations. Keep the configured event publisher ID
and cursor retention consistent between the target CLI and application.

The `snapshot` and `apply-indexes` commands below run at the admin CLI prompt;
`java`, `curl`, and `kill` run in your operating-system terminal. Replace all angle-bracket
placeholders, and paste multi-line CLI examples as a single line if needed by your terminal.
DuckDB's `postgres` extension must be available to the importer; its first installation may need
network access. `--memory-limit` is per worker, not a total process limit.

## Overview

The analytics store already exports most operational data to Parquet managed by DuckLake. The
snapshot commands turn that output into a versioned, verifiable restore format:

```text
PostgreSQL -> analytics exporters -> immutable DuckLake files
                                       |
                          epoch-aligned snapshot manifest
                                       |
                          independent ZIP parts + checksums
                                       |
                                       v
empty migrated PostgreSQL <- transform/load <- extracted Parquet
          |
          v
control state + validation -> resume Yaci Store
          |
          v
manual `apply-indexes`
```

A snapshot restores to **one Cardano point**: the last block of the newest epoch that every required
table fully supports. It is deliberately *not* the newest exported block, because daily and epoch
exports advance independently and the newest block can be ahead of the derived state that must
accompany it.

<Callout type="warning">
A snapshot is not a database backup. It carries what the analytics exporters produce, and every
field it cannot carry is declared in the manifest. Read [Known limitations](#known-limitations)
before treating a restored database as equivalent to a synced one.
</Callout>

## Commands

| Command | Purpose |
|---|---|
| `snapshot inspect` | Read-only: candidate consistency point, coverage, limitations, blockers |
| `snapshot export` | Package the pinned DuckLake file set into independent ZIP parts |
| `snapshot verify` | Verify a manifest and every part, without touching a database |
| `snapshot import` | Load a verified snapshot into an empty, migrated schema |
| `snapshot import-status` | Show the state of any import recorded in the configured schema |
| `snapshot validate` | Run the offline validation levels against the imported database |

All of them use the datasource and schema from the same Spring configuration the admin CLI already
uses. Passwords are never accepted as command arguments and never appear in a manifest, report or
log.

## Producing a snapshot

Configure the source for [DuckLake analytics export](/docs/v2/analytics/overview), including the
ledger-state data required by the snapshot specs. The `ledger-state,analytics` profiles are the
usual source setup; enabling the analytics property alone does not populate historical data.

Before inspecting or exporting, backfill daily partitions from the beginning of the chain and
epoch partitions from the first non-Byron epoch, including empty partitions. Snapshot inspection
derives this epoch boundary from the exported blocks, matching analytics gap detection.
`epoch` and `epoch_param` hold rows for Byron epochs too, so their partitions are required from
epoch 0; analytics exports them automatically, and other epoch tables need no Byron records.
The configured PostgreSQL datasource must be the source
of the analytics export: its `analytics_export_state` journal provides completion evidence.
Snapshot inspection compares each required partition's recorded row count with the pinned catalog;
missing, failed, or mismatched partitions block export.

Stake balances use the lossless `stake_address_balance_snapshot` exporter, enabled by default
when analytics is enabled. Include it in `yaci.store.analytics.enabled-tables` if you use an
allowlist, and backfill existing installations from retained,
unpruned `stake_address_balance` history. The existing `stake_address_balance` analytics exporter
continues to produce daily downsampled data and cannot be used for restore. Existing snapshots with
the old stake-balance spec must be regenerated.

Analytics-only installations can disable this exporter with
`yaci.store.analytics.exporter.stake_address_balance_snapshot.enabled=false`.
Snapshot export requires the lossless relation to be complete.

While the source analytics process is running, enable its admin API:

```properties
yaci.store.analytics.enabled=true
yaci.store.analytics.admin.enabled=true
```

Backfill the lossless relation through the source's analytics API. Dates are inclusive; replace the
placeholders with the first chain date and the last fully exportable day:

```bash
curl -X POST 'http://localhost:8080/api/v1/analytics/admin/export/table/stake_address_balance_snapshot/range?startDate=<FIRST_CHAIN_DATE>&endDate=<LAST_COMPLETED_DATE>'
```

Other daily tables use the same endpoint with their exporter name. Epoch tables use the following;
for `epoch` and `epoch_param`, start at epoch 0:

```bash
curl -X POST 'http://localhost:8080/api/v1/analytics/admin/export/table/<TABLE>/epoch-range?startEpoch=<FIRST_NON_BYRON_EPOCH>&endEpoch=<LAST_COMPLETED_EPOCH>'
```

Check the response's successful-partition count and the export logs. Backfill requires retained
source history; re-exporting an already pruned source cannot recover discarded rows. Do not delete
completion records simply to silence a coverage error.

Stop the analytics process cleanly and close its catalog connections before inspecting or
packaging. Keep it stopped until packaging finishes. If inspection identifies missing partitions,
restart analytics to backfill them, then stop it again before repeating inspection.

### 1. Inspect

```bash
snapshot inspect --data-dir ./data/analytics --work-dir ./.snapshot-work --verbose
```

Reports the consistency point that would be selected, which tables constrained it, how far it sits
behind the newest exported block, the estimated archive size, every declared limitation, and any
blocker. It does not modify the source database or catalog.

Example output:

```text
Consistency point: epoch 308, block 5091913, slot 131846389
  Block hash     : 8082778ebea46f3caaa814b3628de17a69aa32e5b7366f419412bec93db6281e
  Newest export  : block 5095924 (the point is 4011 blocks behind it)
  Limited by     : adapot, address-utxo, block, drep-dist, epoch, epoch-param, epoch-stake, ...
Coverage: 44 table(s), 22429 file(s), 104297087 row(s), about 7.2 GiB
```

### 2. Export

```bash
snapshot export --data-dir ./data/analytics \
                --output /path/to/output \
                --work-dir ./.snapshot-work \
                --part-size 8GiB --unsigned --allow-incomplete
```

For a manual qualification run, use `--target-epoch <E>` to select a point several completed epochs
behind the source tip. This lets the restored instance replay several epoch transitions.
`--allow-incomplete` acknowledges declared losses; it never bypasses failed coverage or integrity
checks.

Export packages files an exporter has already written; it never reruns or replaces an analytics
exporter. It pins one DuckLake catalog snapshot, resolves the exact immutable file set, streams it
into parts, re-reads and checksums every part, and publishes the manifest last with an atomic rename.

| Option | Default | Purpose |
|---|---|---|
| `--part-size` | `8GiB` | Target size per ZIP part. A Parquet file is never split. |
| `--min-confirmations` | `2160` | Blocks the point must sit behind the newest exported block |
| `--target-epoch` | `0` | Select an older completed epoch; `0` chooses the newest supported one |
| `--allow-incomplete` | `false` | Package even though the snapshot declares limitations |
| `--unsigned` | `false` | Acknowledge that no signature will be produced |
| `--spec-file`, `--allow-custom-specs` | – | Operator-supplied specifications |

<Callout type="info">
Export attaches the original catalog read-only and holds its database lock through packaging.
It refuses a catalog held by another writer. It never copies a live database file, which could
omit committed WAL entries. Analytics writes, compaction, and garbage collection must stay stopped
throughout export.
</Callout>

### Archive layout

```text
yaci-preprod-e308-<id>.manifest.json
yaci-preprod-e308-<id>.part-00001.zip
yaci-preprod-e308-<id>.part-00002.zip
...
SHA256SUMS
```

Parts are **independent** archives, not a spanned ZIP: each can be retried, mirrored and verified on
its own. Entries are stored uncompressed, because DuckLake already writes Zstandard-compressed
Parquet and re-deflating costs hours of CPU for a fraction of a percent. Paths inside a part are
relative to the analytics data directory, for example
`main/block/date=2026-08-24/ducklake-....parquet`.

`SHA256SUMS` is in the usual format, so parts can be checked with standard tools before any Yaci
Store code runs:

```bash
sha256sum -c SHA256SUMS
```

### Manifest

The canonical JSON manifest records the snapshot format version and id, the producing release, the
complete consistency point, the pinned DuckLake catalog snapshot, the module set and pruning
settings, the PostgreSQL schema and Flyway fingerprints, every archive part, and per table: the
specification id, version and SHA-256 digest, the load mode and cutoff rule, the row count, the
key, the observed source column types, bounds, and every packaged file with its digest.

It contains no database URL, user name, password, host name or local absolute path. Keys are sorted
and nulls omitted, so serializing the same manifest is deterministic. Separate exports have new
snapshot IDs and timestamps, even if they package the same file set.

## Restoring a snapshot

Preflight (`--dry-run`) checks manifest compatibility, database state, part existence, and sizes.
It does not hash the archives. A real import verifies each part's digest once before extraction,
then verifies the extracted files. Use `snapshot verify` for a standalone integrity check.
Unsigned imports require explicit `--allow-unsigned`.

### 1. Prepare the target schema

Schema fingerprints exclude the known reward-calculation working tables (`ss_*` names explicitly
listed by the snapshot component), which are recreated by aggregate jobs and absent in a fresh
schema. Other table-definition differences still block import. Snapshots produced before this
correction must be regenerated; do not edit the manifest fingerprint by hand.

Use **the same Yaci Store release named in the manifest** to initialize an empty target. Run your
actual application, including an application that uses Yaci Store as a library, with its intended
profiles and store flags. For example, select a separate PostgreSQL schema in `target.properties`:

```properties
spring.datasource.url=jdbc:postgresql://localhost:5432/yaci?currentSchema=snapshot_test
spring.flyway.schemas=snapshot_test
spring.flyway.default-schema=snapshot_test
```

Supply your usual datasource credentials, network settings, and `store.*.enabled` flags in that
file, then run:

```bash
java -jar /path/to/your-yaci-store-app.jar --spring.config.additional-location=file:/path/to/target.properties --store.schema-only=true
```

This mode runs the application's existing Flyway migrations, records its installed and enabled
stores, closes the migration context, and exits successfully. It exits with a nonzero code on
failure. It automatically suppresses sync, store jobs, and the normal application context, even
when `store.sync-auto-start=true`. Flyway creates the configured schema; manual `CREATE SCHEMA`
is unnecessary when the database user has permission. Custom Flyway locations remain supported.

For Docker Compose, use a one-off container with the target configuration mounted:

```bash
docker compose run --rm <service> --store.schema-only=true
```

Flyway may create tables for disabled stores because it discovers migrations on the classpath.
The target-local `_yaci_store_schema_profile` table records the import scope; table existence does
not select stores. The admin CLI reads this record. If the CLI explicitly configures a store flag
that disagrees with it, import stops with a configuration error. Use the same target configuration
and profiles for the application and CLI. An existing empty, migrated target can run schema-only
mode once to create this record without recreating its tables.

Only enabled stores are restored and validated. Required dependencies must also be enabled;
block, cursor, and era state are required to resume sync. Disabled stores' chain tables must stay
empty. New manifests carry per-table schema fingerprints, allowing a smaller target application
to import without matching unrelated source tables or Flyway history. Older manifests without
these fingerprints require the whole schema fingerprint to match; otherwise regenerate the
snapshot. Custom application tables still need explicit snapshot specifications.

Keep Yaci Store stopped during import. Remove `store.schema-only=true` (or set it to false) before
starting normal sync after validation. The admin CLI also runs Flyway at startup, against the
configured schema and with the migrations on its own classpath. On a target initialized as above
this finds nothing to apply. Do not use it to initialize a target: it does not record the store
profile, so import refuses that schema.

Do not run `apply-indexes` first. The base tables, primary keys and unique constraints created by
Flyway are required; the optional read indexes from `index.yml` and `extra-index.yml` are applied
afterwards.

### 2. Verify

```bash
snapshot verify --manifest /path/to/yaci-preprod-e308-<id>.manifest.json
```

### 3. Preflight

```bash
snapshot import --manifest <manifest> --work-dir /path/to/work --dry-run --allow-unsigned
```

Import refuses to run unless the archive verifies, the network and protocol magic match the
configured instance, selected tables have matching schema fingerprints and specification versions
and digests, every table in the target schema has a classification,
and the schema is either empty or holds a matching incomplete import journal.

A network mismatch is never overridable. Preflight reports selected and skipped tables. The import
scope is saved in the journal and cannot change on resume or validation. All archive parts and
files are still verified and extracted, so a scoped restore needs space for the full archive.

### 4. Import

```bash
snapshot import --manifest <manifest> \
                --work-dir /path/to/work \
                --allow-unsigned \
                --workers 1 \
                --memory-limit 1GB \
                --min-free-disk-gb 20
```

| Option | Default | Purpose |
|---|---|---|
| `--workers` | `1` | Bounded worker count; each gets its own connection, memory limit, spill directory and transaction |
| `--memory-limit` | `1GB` | Per-worker DuckDB memory limit |
| `--min-free-disk-gb` | `20` | Minimum free space required at `--work-dir` during preflight |
| `--keep-extracted` | `false` | Keep extracted Parquet after a successful import |
| `--dry-run` | `false` | Preflight only; write nothing |
| `--validate` | `false` | After a successful import, run `snapshot validate --mark-ready` in the same command |

<Callout type="warning">
`--min-free-disk-gb` checks the **work directory** before loading; it is not a continuous disk-space
monitor. Allow room for extraction and DuckDB spill, and monitor disk usage during the run. Make sure the
PostgreSQL data volume separately has room for the restored database, which is much larger than the
archive.
</Callout>

The work directory needs roughly the uncompressed archive size for extraction, plus spill space per
worker.

### 5. Validate

```bash
snapshot validate --manifest <manifest>
```

Four levels are defined; the first three are offline and must all pass before sync is enabled.

1. **Artifact** — explicit unsigned acknowledgement, part digests, ZIP traversal/duplicate/size
   protections, exact required part set, per-file digest after extraction.
2. **Schema and load** — selected table fingerprints, per-table row counts after cutoff, tables
   that must be empty really are, required non-null column values, sequence values, and a journal
   matching the exact manifest.
3. **Semantic** — the manifest point equals the last imported block *and* the final cursor, the
   retained block and cursor tails have a continuous previous-hash chain, no rows beyond any
   table's declared cutoff, era rows point at real blocks, `address_utxo` has one row per
   `(tx_hash, output_index)` with valid JSONB amounts, exactly one lovelace entry, a matching
   lovelace total and a resolved block number.
4. **Application acceptance** — an operational gate, listed by the command: start with
   `store.sync-auto-start=false` and smoke-test reads, start against a node and confirm the point is
   accepted, observe the normal restart rollback and replay, sync past the point, restart, kill and
   recover, and exercise a rollback within retained cursor history.

Before starting chain sync, run:

```text
snapshot validate --manifest <manifest> --mark-ready
```

On offline validation success, this marks the import `READY` and drops its temporary journal.
It does not certify application acceptance. Run it before syncing: after new blocks arrive, the
database is intentionally beyond the manifest's point and its original row counts. Preserve the
validation output for the acceptance record.

`snapshot import --validate` does the same in one command: after the import finishes, it runs every
offline level and, if all pass, marks the import `READY`. If validation fails, the import is left in
`VALIDATING`; fix the cause and rerun `snapshot validate`.

### 6. Apply indexes

```bash
apply-indexes                        # default read indexes plus extra indexes
apply-indexes --skip-extra-indexes   # default read indexes only
```

Index creation is **not** part of snapshot import. The importer never creates, drops, defers or
rebuilds an admin-managed index; if some already exist it warns that loading will be slower and
leaves them alone. Index build time is reported by the normal admin CLI workflow and is measured
separately from the heap load.

### UTxO import memory

The flattened UTxO export has one row per asset. Import reconstructs each output's amounts using
an ordered list aggregate, whose intermediate state cannot always spill to disk. Workers now
split each existing UTxO batch into execution slices by a hash of `(tx_hash, output_index)` before
aggregation. All assets of an output stay together, even across Parquet files. The number of
slices is estimated from the input size and the worker's memory budget. A DuckDB out-of-memory
failure rolls back the batch and retries with twice as many slices.

This trades repeated Parquet scans for a smaller aggregation working set. Larger `--memory-limit`
values allow fewer slices and potentially faster loading. `--workers` controls how many batches
run concurrently; the memory limit applies separately to each worker. For a smaller machine,
the defaults are `--workers 1 --memory-limit 1GB`, leaving RAM for Java, PostgreSQL and the operating
system. Scanning, joining and one output's assets must still fit; arbitrarily small limits are
not supported. A synthetic multiasset integration test covers a 128 MB DuckDB budget, which is
not a total-machine RAM requirement.

Execution slices do not change the specification, manifest, or persisted batch IDs. The entire
original batch and its journal entry commit together. Existing imports can resume with the new
CLI and a different memory limit without regenerating the snapshot or clearing data.

## Resuming an interrupted import

Work is a content-addressed queue of `(table, batch)` items. A batch's rows and its journal record
commit in the **same transaction**, so a recorded batch is committed and an unrecorded batch left no
rows. Re-running the same command resumes:

```bash
snapshot import-status          # what was completed
snapshot import --manifest <manifest> --work-dir <dir> --allow-unsigned
```

The report distinguishes batches skipped (already committed) from batches loaded. Batch identity is
derived from the snapshot id, the table, the transform version and the sorted digests of the batch's
input files. Resume also checks the canonical digest of the entire original manifest under the
import lock. You may change `--workers`; you must keep the same manifest, specifications, batch
sizes, and archive files. Missing or duplicate manifest table entries are rejected, including
entries for tables with zero rows.

Deleting a partial import is never an automatic recovery action. Clearing a non-empty schema is a
separate, explicit operation.

## Manual acceptance test

Use a disposable target and retain an independently synced reference database. Complete the
export/import workflow above, choosing an older target epoch so several epoch transitions can be
replayed. Preserve the build commit, manifest, logs, timings, and validation results.

| Test | Procedure | Required result |
|---|---|---|
| Export coverage | Inspect the source, then export and verify the archive. | No blockers; all part digests match. |
| Import crash recovery | After batches commit, terminate only the test importer with `kill -9 <IMPORTER_PID>`. Restart the CLI, inspect `snapshot import-status`, and repeat the identical import command. | Committed batches are skipped; remaining batches complete without duplicates. |
| Offline restore | Run `snapshot validate` before starting sync. Compare representative historical data at the same cutoff with the reference. | All offline checks pass; blocks, UTxOs, pool margin rationals, and latest stake balances at or before the cutoff agree. |
| Node intersection | Mark ready, apply indexes, and start the target with syncing enabled. | The node accepts an intersection; normal startup rollback/replay succeeds and syncing advances. |
| Epoch accounting | Sync through at least three subsequent epoch boundaries. Compare each newly calculated epoch with the reference. | Reserves and treasury match exactly; no failed AdaPot jobs. |
| Graceful restart | Stop the restored application normally and restart it. | It resumes from its persisted state and catches up. |
| Sync crash recovery | Terminate only the restored test application with `kill -9 <RESTORED_APP_PID>` during syncing, then restart. | Recovery completes and forward sync resumes without data errors. |
| Retained-history rollback | Using a controlled test node or replay setup, cause an actual rollback within retained cursor history, then replay. | The final state matches the reference; restarting alone does not satisfy this test. |

After successful forward sync, compare at identical epochs or chain points rather than comparing
an advancing source's totals with the original snapshot cutoff. Capture query/API smoke-test results
as well as accounting results. These checks qualify only the tested network and profile; repeat at
mainnet scale before claiming mainnet readiness.

### Rejection tests

Use copies of the archive and a separate disposable target. Do not alter the successful run's
original manifest or journal.

| Change | Expected rejection |
|---|---|
| Remove a part, or change bytes in a copied part. | `snapshot verify` fails; import does not load rows from the damaged archive. Dry-run alone does not detect same-size byte changes. |
| Remove or duplicate a table entry in a copied manifest. | Import rejects the manifest before loading. Include a zero-row table in this test. |
| After interrupting import, change the manifest but keep its snapshot ID. | Resume rejects the manifest digest mismatch. |
| Configure a different network/protocol magic. | Import rejects the network mismatch. |
| Import into a target containing chain data with no matching journal. | Import rejects the non-empty target. |
| Inspect/export while another process holds the catalog open for writes. | Catalog access fails with instructions to stop analytics. |

Inspect the command output and validation report. The interactive CLI catches command errors, so
its process exit code alone is not an acceptance result.

## Troubleshooting

| Message or symptom | Action |
|---|---|
| No completed export record | Backfill the reported partition, including an empty partition, using the correct source database. |
| Catalog row count differs from export journal | Check that the data directory and source datasource belong together. Investigate failed/repeated exports; repair and re-export affected data before packaging. |
| Missing `stake_address_balance_snapshot` relation | Restart with the updated analytics build, ensure the lossless exporter is not disabled or excluded by an allowlist, and backfill retained history. |
| Catalog cannot open read-only | Shut down the analytics process cleanly. If it crashed, recover and close it normally before trying again. |
| Schema or spec mismatch | Use the matching build and complete schema. Regenerate old snapshots that used the downsampled stake-balance spec. |
| Resume manifest digest mismatch | Restore the original manifest and archive. Do not edit the journal to force a match. |
| Unsupported PostgreSQL JDBC setting | The DuckDB/libpq write path supports a narrower connection configuration; use a supported configuration rather than silently dropping TLS or connection settings. |
| Not enough disk space | Increase work-directory capacity and separately check PostgreSQL data/WAL capacity. Lower worker count if spill pressure is high. |

## Table specifications

Each table's snapshot behaviour is a versioned YAML resource owned by the module that owns the
target table, beside its migrations:

```text
stores/blocks/src/main/resources/snapshot/block.yml
stores/utxo/src/main/resources/snapshot/address-utxo.yml
stores/utxo/src/main/resources/snapshot/sql/address_utxo_v2.sql
aggregates/adapot/src/main/resources/snapshot/reward.yml
```

A build task collects them into the snapshot component with a deterministic index, so the admin CLI
reads them without classpath scanning, a Spring context, or any store implementation class.

<Callout type="info">
A specification is **additive**. It describes output an existing exporter already produces and never
registers, schedules or executes one. Built-in `TableExporter` classes, `CustomTableExporter`,
`TableExporterRegistry`, exporter properties, the analytics admin endpoints and
`application-custom-exporters.yml` all keep their current behaviour and format, and analytics works
unchanged with no snapshot specification present.
</Callout>

### Anatomy

```yaml
snapshot-table:
  id: pool-registration
  spec-version: 1
  module: staking
  kind: CHAIN_DATA
  restore: IMPORT

  source:
    exporter-id: pool_registration
    ducklake-relation: pool_registration
    partition:
      strategy: DAILY
      column: block_time

  consistency:
    cutoff:
      type: SLOT_LTE
      column: slot

  import:
    target-table: pool_registration
    mode: SQL
    select-resource: classpath:/snapshot/sql/pool_registration_v2.sql
    transform-version: 2
    dependencies: [block]
    columns:
      pool_owners:
        source: pool_owners
        converter: "varchar-to-jsonb"
      relays:
        source: relays
        converter: "varchar-to-jsonb"
    use-target-defaults: [update_datetime]
    batch-boundary: FILE_SET
    batch-size: 64

  validation:
    key: [tx_hash, cert_index]
    bounds: [slot, epoch]
    required-columns: [tx_hash, cert_index]
```

### Import modes

| Mode | Purpose | Java needed |
|---|---|---|
| `DIRECT` | Identical source and target names, compatible types | No |
| `MAPPED` | Renames, named converters, constants, omissions, target defaults | No |
| `SQL` | One trusted read-only DuckDB `SELECT` for joins, grouping or reshaping | No table class |
| `HANDLER` | Operational lifecycle state that is not a projection of exported rows | Small SPI |

Adding an ordinary table needs a migration and one YAML specification. Adding an ordinary column
needs an update to that specification. Java is needed only for a genuinely new reusable converter or
a new control-state handler.

### Column accounting is total

Columns not listed under `import.columns` are matched by identical name, and only when their types
are compatible. After explicit mappings, `ignore-source-columns` and `use-target-defaults` are
applied, **every** source and target column must be accounted for. An unknown source column, an
unwritten target column, a rename that has not been declared, or a `NOT NULL` target left to a
default it does not have is an error at planning time.

This is the point of the design: a permissive name-based mapper silently writes NULL when a column
is renamed or added, producing a database that looks populated but is wrong.

### Named converters

| Converter | Use |
|---|---|
| `timestamp-to-epoch-seconds` | `timestamptz` export column to a Unix-seconds `bigint` |
| `varchar-to-jsonb` | JSON text to a `jsonb` column |
| `to-smallint`, `to-integer`, `to-bigint`, `to-decimal38`, `to-varchar` | Checked numeric conversion; overflow fails the batch |
| `uuid-v5:<key columns>` | Deterministic RFC 4122 v5 id for a row whose export omits it |
| `null-literal` | Explicit null |

`uuid-v5` derives an id from a fixed namespace and the row's natural key, so re-importing the same
snapshot reproduces byte-identical ids.

### SQL transforms

`SQL` mode references a versioned resource rather than embedding a query in YAML or Java:

```yaml
    mode: SQL
    select-resource: classpath:/snapshot/sql/address_utxo_v2.sql
    transform-version: 1
    dependencies: [block]
    batch-boundary: WHOLE_PARTITION
```

The importer supplies `${files}`, `${dep.<spec id>}`, `${cutSlot}`, `${completedEpoch}` and
`${uuidNamespace}`. A resource must be a single read-only `SELECT` (a leading `WITH` is allowed) and
may not contain DDL, transaction control, `ATTACH`, `COPY` or `INSTALL`.

`WHOLE_PARTITION` batching is required whenever a transform groups rows: a partition split across
two batches could emit the same grouped key twice.

When a transform changes cardinality, declare `validation.source-key` so the manifest records the
number of rows the import will actually produce, rather than the number of rows it reads.

### Custom specifications and trust

Executable mapping rules are never taken from a downloaded archive. The archive carries only
specification ids, versions and digests; the rules themselves come from the local installation, and
the local digest must equal the manifest digest.

Operator specifications are loaded only from an explicit `--spec-file` and require
`--allow-custom-specs`. A custom specification can never override a built-in one, and two
specifications can never claim the same target table.

## Known limitations

A snapshot's manifest lists every declared limitation, and `snapshot validate` repeats them. For a
snapshot produced from the current analytics export:

- **`address_utxo.owner_addr_full`** is not present in the flattened export and cannot be recovered
  from it. It is populated only for addresses longer than 500 characters, so it is null for
  effectively all rows in practice, but the limitation is real and recorded. A later
  snapshot-format revision will add a lossless projection.
- **Address balance history is not restored.** `address_balance` and `address_tx_amount`
  remain lossy analytics projections and are left empty, along with the `*_current` caches.
  `stake_address_balance` is restored from the separate lossless
  `stake_address_balance_snapshot` export, and `account_config` is seeded at the snapshot point.
- **`block_cbor` and `transaction_cbor`** have no analytics export.
- **`epoch_nonce`** and **`ptr_address`** have no analytics export.
- **`address.stake_credential`** is not exported and is not derivable from what is.

<Callout type="warning">
**Snapshots produced before the margin fix cannot run the ledger-state profile.** The exporter now
carries `pool_registration.margin_numerator` and `margin_denominator`, because the AdaPot reward
calculation reads the exact rational rather than the float. An older export lacks them, and
`snapshot inspect` will refuse it: the `pool_registration` transform cannot be prepared. Re-export
that relation (see below) before producing a snapshot intended for a ledger-state instance.
</Callout>

<Callout type="warning">
**Older stake-registration exports must also be refreshed.** The lossless registration projection
now includes `deposit`, preserving explicit registration deposits and nullable deregistration
refunds. Stake-registration snapshot spec version 2 requires this column during inspection.
Do not add `deposit` to `use-target-defaults`: that would silently discard ledger data.
Refresh the `stake_registration` relation and its export state using the widening procedure below,
then let analytics backfill it from retained PostgreSQL history and generate a new snapshot.
The `stake_address_balance_snapshot` relation does not need to be rebuilt for this change.
</Callout>

<Callout type="warning">
**Older UTxO, withdrawal and metadata exports must also be refreshed.** The `address_utxo`,
`withdrawal` and `transaction_metadata` exports now carry `tx_index`, the transaction's position in
its block, and their snapshot specs (version 2) require it. `address_utxo` also carries
`asset_index`, each asset's position in `amounts`, so a restore keeps the original element order.
Exports made before this change also lack the Byron `epoch` and `epoch_param` partitions; analytics
backfills those on its own after the upgrade. Refresh those three relations and their
export state using the widening procedure below. The source database must already hold `tx_index`
for its history; a schema migrated in place from a release without it has NULLs and must be resynced.
</Callout>

### Widening an exporter

The DuckLake writer creates a relation once with `CREATE TABLE AS SELECT ... LIMIT 0` and inserts
into it thereafter, so adding a column to an exporter does not change an existing relation. To pick
up the new columns, drop that relation and its export state so it is rebuilt:

```sql
-- against the analytics catalog
DROP TABLE ducklake_catalog.pool_registration;
-- against the operational database
DELETE FROM analytics_export_state WHERE table_name = 'pool_registration';
```

The next export run recreates the relation with the wider schema and re-exports its partitions.
The size depends on the network and retained history; plan the re-export accordingly.

A snapshot with a non-empty limitations list is a development snapshot. `snapshot export` refuses to
package one unless `--allow-incomplete` is given.

## Safety notes

- Extraction rejects absolute paths, `..` traversal, entries resolving outside the work directory,
  duplicate entries, symbolic links, entries not declared in the manifest, and entries whose size
  differs from the manifest.
- Import takes a PostgreSQL advisory lock, so two imports cannot run against one database.
- Every identifier that reaches generated SQL is validated and quoted.
- The DuckDB PostgreSQL attachment exposes every schema on the server, so all generated SQL is
  schema-qualified with the configured target schema.
- Credentials are redacted from messages and exceptions.
